## 实现与边界

- 楼体、路面、水面和桥各占一个静态批次，按 3×3 块分桶；可见范围内每桶提交四个图层，所以单块的提交数随可见桶数增长（默认约 2–3 个桶，即 8–12 次），不再是一个全场景批次。路灯、栏杆和街具共用一个实例批次，停放车辆共用另一个。加上单块地形，单块提交数 = 可见桶数 × 4 + 2 + 1。`?buckets=N` 可改桶边长、`?nobatch=1` 退回单桶，用于对比。树、山和独立 GLB 单独计数。树的全场景批次数上限是树种数 × 2，种数由 `look/trees.ts` 的 builders 派生。IDOK-71 新树接入 `treeGeometry(kind) → {near, far, material}` 即可沿用矩阵、顶点色和种子色差。
- 地标同一 LOD 中共享几何和不透明材质的静态叶节点可以实例化。大型单体网格把连续 256 个三角形作为一组，分别对主相机、镜像相机做包围盒测试。两遍共用同一索引缓冲区，各提交自己的可见范围。市场的大型单材质网格因此仍只需一次材质提交。碰撞节点使用独立索引。
- 程序楼远景保留主体、墙和坡屋顶，分块包围球离相机 280 m 以外时略去女儿墙和屋顶设备。树种按种子在 240–316.5 m 切换低模，在 1380–1500 m 渐隐。谷地高度雾仍逐像素计算；远裁面取与天空完全混合的 7500 m。流式半径仍按资源用途分开，玩家近旁保留碰撞所需的精细分块。
- 清晰天气、相机静止、视锥和水位未变时可以复用最近 60 ms 的倒影；**街块仍在流式加载时也允许复用**（pending 不再阻塞复用）。相机移动、缩放、切换水位或分辨率即刷新，步行和过场逐帧刷新。水纹和直接视图始终逐帧绘制。
- `pipeline/hidden_faces.py` 在 gltfpack 之前只改渲染索引。去掉同一图元内顶点完全重合、绕序相反、边界两侧均有实体延伸的三角形，以及低于脚下地形支撑点下界的朝下三角形。地形下界同时考虑 4、8、32 m 三档采样。跨大范围无法证明遮挡的面、共享实例的底面、碰撞节点和双面薄片保留。
- 楼脚墙顶点乘 0.92 的暗部系数，凹角另乘 0.98。树冠沿用分部件高度插值的顶点色。实时阴影提交数为 0。
- 首屏远水遮罩用与原始 overview.png 相同的两点取样在离线生成时编码为每 8 m 一位。旧清单继续在浏览器中从位图生成遮罩。

## 复测方法

生成世界、地标并构建后运行 `node scripts/perf-audit.mjs captures/after`。可用 `AUDIT_DIST` 指向另一份已构建的站点。每档六次独立浏览器上下文，从相同默认出生点记首帧，再设置相机并等待范围内街块、树和地标加载完成。飞行项包括六个预设机位和 verify:flight 的 W 键前进段。其余机位固定，太阳固定在 10 时。桌面 960×540，手机模拟 390×844、触控、4× CPU 降速，使用同一台 Mac 的 Metal GPU。

固定机位预热 6 帧、采样 120 帧，运动段采样 60 帧。calls 和三角形按实际 WebGL 绘制求每帧算术平均，包含刷新倒影的帧。p50/p95 取连续 rAF 时间戳之差。几何内存为 WebGL bufferData 请求的缓冲字节数，包含索引和实例数据。贴图内存按纹理尺寸、格式和 mip 估算，含镜面颜色附件，不含深度渲染缓冲、驱动开销和 CPU 堆。手机数据为模拟结果。

## 持续移动段的主线程耗时

在上一轮交付代码上，用 Chromium DevTools Protocol 的 CPU Profiler 包住相同的手机模拟 W 键前进段。未压缩函数名的生产构建中，主线程 2150 ms 的采样窗口内，街面生成 `streetGeometry` 栈累计约 329 ms，地标剔除 `update` 约 127 ms，街块静态批次重建约 78 ms。耗时包含子调用。修复后同一路线的主线程采样窗口为 1739 ms，街面细分移出主线程，地标剔除累计约 75 ms。帧时间验收另用压缩发布构建并关闭 Profiler。

街块载入时，一个复用的 Web Worker 按原有高程插值、细分和法线算法生成街面。顶点、法线、顶点色、街具实例及人行道碰撞数组通过 transferable buffer 交回主线程。用六个实际街块比较新旧计算，465,498 个街面顶点及其关联数组逐元素一致。地标可见范围沿主相机与镜像视锥各外扩 8 m。在只平移且累计不足 8 m 时复用分组和索引；转动、缩放、水位变化或跨过阈值立即重算，刚启用的 LOD 也会重新分类。

## 验收观察

- 12 组平均 draw calls 降低 33%–44%，提交三角形降低 40%–86%。持续移动的桌面与手机各三对，六对 p95 均持平或缩短。固定机位仍受 60 Hz 刷新限制，p95 在 16.7–16.8 ms 间波动，部分机位较基线高 0.1 ms。
- 24 张同机位图中，近景街角、王城拱门、桥墩、树冠及远山的轮廓无明显退化。地标末档在最后 60 m 渐隐，590、620、650 m 的覆盖率依次为 1、0.5、0，651 m 停止提交。涉水桥墩保留底盖。
- 首屏远水遮罩压缩后嵌入清单（额外 7120 个编码字符）。远水的 8786 个三角形与基线一致，山体噪声缓存前后的顶点色一致。
- 在 4c937d0 上从原始数据运行 `QA_NATIVE_GPU=1 WALK_FIXED_STEP=1 npm run qa`，九项全部通过（飞行覆盖 322/322 块，照片匹配 126 张）。最终预打包 GLB 另跑 `npm run audit:landmarks -- --strict`，贴地失败 0/43。剔面单测 3 项通过。补充全城审计在 main 与 PR 的位置和分类完全一致，共 5 处地标占道、2 处地标重叠及 2 处桥面接缝高差。

### 扩区分块预算（IDOK-114）

客户端预算集中在 `web/src/tile-grid.ts`。GL04 主线程解析和场景挂接分别按 5 ms / 4 ms 调度，每个非空队列每帧至少推进一项；昂贵的单项可以超出预算。近景块最多 180 个（含在途），总块请求并发 8，出生点优先环并发 6。树块并发 6，优先环繁忙时限制为 1，网络请求结束即可补位。地形和树木共用 256 m 空间索引，加载和保留半径随渲染距离预设变化。远景地形共用一个索引缓冲，水面只提交视锥中的块，扩区建筑代理合批绘制。使用 `PERF_CPU_RATE=4 npm run perf -- --expansion` 复测，每个机位的 `loadMs` 包含导航和等候近景块、树块就绪的耗时。

道路校正每轮将道路系统拆成 768 m 子域，外加 160 m 重叠带；`pipeline/road_grading.py` 已用 4 个工作线程求解子域，在本轮所有子域完成后更新残差。SG 此前 50 分 02 秒的冷构建超出 45 分钟目标。

构建使用 `npm run world -- --workers 4` 并行压缩和写出块，最多保留 4 个待写块，manifest 仍按行列排序。可传 `--workers 1` 做串行对照。DEM 每次插值 128 行。默认框对齐后为 44 × 68 块，共 2992 块。Terrarium z14 需要 x=13209–13214、y=6997–7005 全部 54 张；IDOK-2 的旧包只有中间 16 张。

总览地形按 256 m 块拼入同一索引缓冲。相机周围使用 32 m 网格，远处步长为 128 m，粗细交界共用边界顶点。近景块就绪后从总览索引移除对应三角形。新增俯视机位用 `?cam=balijie`、`?cam=zengpiyan`、`?cam=guilinta`、`?cam=eastBoundary`；用相同名字传给 `?spawn=` 请求就地落脚。东侧机位在龙门大桥以东，东界为 110.352 E。四处步行机位分别取俯视中心最近的可通行街道。

扩区山峰近景按 2048 m 扇区、1600 m 预取距离调度，一次解码一个扇区；离开后释放 GPU 几何。远景建筑使用一个实例批次，3600 m 内最多 768 个体块。远水合并相邻行中同一水位和跨度的矩形。运行 `npm run perf -- --expansion` 输出俯视与人视截图、帧时间、draw calls 和三角形数；继而运行 `uv run --locked python pipeline/expansion_overlays.py`，使用截图相机矩阵、32 m 高程样本和原始 OSM 几何制作叠图。

大框的道路高程约束按 768 m 子域求解，每侧额外包含 160 m 邻域。每轮把局部修正应用到同一全局残差，控制点最大修正低于 1 mm 即提前结束，至多四轮。线性系统、初始场及求解器源文件共同决定缓存键。
